# 踩坑记录

按「坑有多深」排序，不是按时间。每条都是实际踩过的，附现象、原因、解法。

---

## 一、飞牛授权：不继承子目录

**现象**

```bash
fnos-cli app config set-authorization-path qbittorrent "/vol3/1000" --perm 6 --yes
# 提示 Updated authorization path
# 但加任务后：
# file_open (/vol3/1000/电影/xxx.mp4) error: Permission denied
```

**为什么难查**：授权确实成功了，`auth-paths` 查得到，UI 里也显示「读写」，但写入就是被拒。日志只有一句 `Permission denied`，不说是哪个目录的问题。

**原因**：飞牛的应用授权是**精确路径匹配**，不是递归授权。`/vol3/1000` 的授权管不到 `/vol3/1000/电影`。

**解法**：把**真正要写入的最后一层目录**单独加一条授权。

```bash
fnos-cli app config set-authorization-path qbittorrent "/vol3/1000/电影" --perm 6 --yes
```

**怎么快速验证是这个问题**：把下载路径改成已授权的那一级目录试一下。能写就说明是子目录权限问题，程序本身没问题。

```bash
./qb-mcp.sh add '<MAGNET>' '/vol3/1000'          # 能写 → 说明是子目录问题
./qb-mcp.sh add '<MAGNET>' '/vol3/1000/电影'      # 不能写
```

## 二、`--perm 7` 会被 UI 认成裸数字

**现象**：用 `--perm 7` 加授权后，飞牛 Web UI 的「可访问的文件」列表里，那一行的权限列显示成一个孤零零的 **`7`**，而其他正常条目显示「读写」。

**原因**：`7` 不是 UI 枚举里的合法值。UI 只认 `6`（读写）/ `4`（只读）这类。传 7 时值写进了配置，但 ACL 没真正下发。

**解法**：统一传 `6`。

| 传值 | UI 显示 | 生效 |
| --- | --- | --- |
| `6` | 读写 | ✅ |
| `7` | `7` | ❌ |

**附带现象**：6 和 7 混着设的时候，会出现"设了新的，之前那条从 7 掉到 6"。统一用 6 就不会。

## 三、两个 qBittorrent，改设置改到了另一个

**现象**：在 WebUI 里把默认保存路径改好了，点保存，提示成功。但用 API 查 `app/preferences`，值还是旧的。

**原因**：飞牛上同时装了「应用中心版」和「手动安装版」两个 qBittorrent，各自跑在不同端口。改的那个不是 MCP 连的那个。

**怎么分辨**

```bash
# 问 MCP：你连的那个实例 WebUI 在哪个端口？
./qb-mcp.sh api "app/preferences" | grep web_ui_port
```

假设返回 `8080`，那你改设置就必须在 `http://<NAS_IP>:8080`，不是 8085。

**另一条线索**：看应用列表里的版本号，两个实例版本通常不同。

```bash
fnos-cli app list | grep -i qbittorrent
```

## 四、MCP 静默忽略高权限端点（假成功）

**现象**

```bash
./qb-mcp.sh api "app/setPreferences" --method POST --params '{"json":"{\"up_limit\":131072}"}'
# 返回：{"message": ""}
# 再次查询：值和之前一样，没变
```

**原因**：MCP 服务对 `app/setPreferences` 这类「全局安全配置」端点做了屏蔽，但早期实现是**静默返回成功**，而不是报错。

**为什么这个坑很毒**：脚本以为成功了，继续往下走，用户在错误的前提上排查半小时。

**解法**：

1. 换专用端点。比如设上传限速用 `transfer/setUploadLimit`，它会被放行且真的生效。
2. 改不了的就接受改不了——比如默认保存路径，只能让用户在 WebUI 手动改一次。

**给实现者的建议**：屏蔽端点时**一定要报错**，别返回空成功：

```json
{"error": "端点被禁止透传: /api/v2/app/setPreferences（涉及鉴权或全局安全配置，防止 AI 锁死访问能力）"}
```

## 五、`qb_list_torrents` 返回的是精简字段

**现象**：列表里「顺序下载」永远显示"关闭"，即使任务明明开着。

**原因**：MCP 封装的列表工具只返回部分字段，没有 `seq_dl`、`ratio`、`eta`。

**解法**：列表改用原生 API 透传：

```bash
./qb-mcp.sh api "torrents/info" --params '{"filter":"all"}'
```

完整字段有 67 个，`seq_dl` 在里面。

## 六、封装工具不支持顺序下载，事后补会改错任务

**现象**：`qb_add_torrent` 的参数里没有 `sequentialDownload`。想在添加后补开，只能找到"刚加的那个任务"再 toggle。

**第一次尝试（错的）**：取"最新添加的一个"。

```bash
# 按 added_on 排序取第一个
torrents/info?sort=added_on&reverse=true&limit=1
```

**为什么错**：这是个共用下载器，别人可能同时也在加任务。取到的可能是别人的，一 toggle 就把别人的顺序下载改了。**实际就这么误改过一次。**

**第二次尝试（还是不够稳）**：加之前记下所有 hash，加之后取差集。

**为什么还不够**：并发添加时差集里会有多个新任务，取第一个仍可能取错。

**正确解法**：直接走原生 `torrents/add`，一次带上参数，并利用它的返回值：

```bash
./qb-mcp.sh api "torrents/add" --method POST --params '{
  "urls": "<MAGNET>",
  "savepath": "/vol3/1000/电影",
  "sequentialDownload": "true",
  "stopped": "false"
}'
```

返回里带 `added_torrent_ids`，这就是**准确**的新任务 hash，不用猜：

```json
{"added_torrent_ids": ["abc123..."], "success_count": 1, "failure_count": 0}
```

## 七、Git Bash 把 `/vol1/...` 改写成 Windows 路径

**现象**

```
错误：savepath 必须是绝对路径
```

传的明明是 `/vol3/1000/电影`，绝对路径没错。

**原因**：Git Bash / MSYS2 有路径自动转换，会把 `/vol1/xxx` 当成 Unix 路径转成 `C:/Program Files/Git/vol1/xxx` 再传给程序。

**解法**：脚本开头关掉转换。

```bash
export MSYS_NO_PATHCONV=1
export MSYS2_ARG_CONV_EXCL='*'
```

**副作用（下一个坑）**：关了之后，MSYS 路径（`/c/Users/...`）原生 Windows 程序也读不了了。读取配置文件路径时要做转换：

```bash
if command -v cygpath >/dev/null 2>&1; then
  CFG="$(cygpath -w "$CFG")"
fi
```

## 八、`MSYS_NO_PATHCONV=1` 下 `curl -o /dev/null` 会失败

**现象**：健康检查里 YTS 明明能访问，却报失败。

**原因**：`/dev/null` 被原样交给 Windows 版 curl，它不认识这个路径，写不进去 → 退出码非 0 → 判失败。但 `-w '%{http_code}'` 仍然打印了 200，所以看到的是"HTTP 200 但判定失败"这种矛盾输出。

**解法**：别用 `-o /dev/null`，直接读正文判断。

```bash
if body="$(curl -s -m 15 "$url" 2>/dev/null)"; then
  printf '%s' "$body" | grep -q '"status":[[:space:]]*"ok"'
fi
```

## 九、python urllib 访问 HTTPS 会握手超时（特定机器）

**现象**：同一台机器，`curl` 访问某个 HTTPS 接口正常，`python -c "urllib.request.urlopen(...)"` 报：

```
_ssl.c:1015: The handshake operation timed out
```

**原因**：这台机器上 Python 的 SSL 栈走不通（可能和代理、证书链或系统 CA 有关），curl 走的是另一套。

**解法**：网络探测统一用 curl，不要用 python urllib。脚本里的 `doctor` 就是这样实现的。

**教训**：诊断脚本不要假设"两种 HTTP 客户端行为一致"。

## 十、顺序下载会拖慢冷种

**现象**：某片开着顺序下载 0.08 MiB/s，关掉后 20 分钟涨到 0.26 MiB/s。

**原因**：顺序下载按块顺序请求，可用的 peer 少时无法并行拉取，效率低。

**判断规则**

| 做种数 | 建议 |
| --- | --- |
| 50+ | 开不开都行，影响不大 |
| < 10 | 关掉，先下完再看 |

**批量关闭**

```bash
./qb-mcp.sh api torrents/toggleSequentialDownload --method POST \
  --params '{"hashes":"<hash>"}'
```

注意这是 **toggle** 不是 set，开着的调一次就关了。要精确控制先用 `torrents/info` 查 `seq_dl` 再决定。

## 十一、文件在 `@appdata` 里，文件管理器看不到

**现象**：下载 100% 完成，但在飞牛「我的文件」里怎么都找不到。

**原因**：应用默认数据目录是 `/volN/@appdata/<app>/`，这是**应用私有区**，文件管理器不显示。

**解法**：把下载目录指到 `/volN/<uid>/...`（用户目录，可见），并做好授权。

如果只是想看已有的文件，也可以在飞牛「应用文件」入口里翻 `@appshare` / `@appdata`，或者给应用设共享。

## 十二、搜片：语言、罗马音、同名不同片

这是最高频的用户体验问题，三种情况都有：

**1. 中文名搜不到**

YTS 是英文站，`可能的爱` 搜不到。

**2. 英文名也搜不到**

韩国片的英文名经常和罗马音对不上。`Seoul Spring` → 无结果，`Seoul-ui Bom` → 找到。

**3. 同名不同片**

`The Attorney` 搜出来的是 2019 年的另一部（6.1 分），而《辩护人》是 `Byeon-ho-in`（2013，tt3404140）。

**解法顺序**

```bash
# 1. 英文名
./yts-api.sh search "英文名"

# 2. 原产地罗马音
./yts-api.sh search "Seoul-ui Bom"

# 3. IMDb ID 直查（最准）
./yts-api.sh details --imdb-id tt3404140
```

**加片前一定核对 IMDb ID**，同名不同片坑过好几次。

## 十三、`torrents/setLocation` 返回成功但文件没动

**现象**

```bash
./qb-mcp.sh api "torrents/setLocation" --method POST \
  --params '{"hashes":"<hash>","location":"/vol3/1000/电影"}'
# {"message": ""}  ← 看起来成功了
# 但查 torrents/info，save_path 还是旧的
```

**原因**：目标目录没有授权给应用，qBittorrent 无法写入，操作实际失败但接口返回了空成功。

**解法**：先授权目标目录，再调 `setLocation`。授权正确后这个接口是可靠的——实测能把 2.26 GB 的文件跨盘搬过去，旧位置自动清空。

## 十四、诊断顺序建议

出问题时按这个顺序查，能省很多时间：

```
1. doctor           → 链路通不通（六项）
2. list             → 任务什么状态
3. log/main         → 最后一屏日志，看具体报错
4. auth-paths       → 目标目录授权了吗
5. preferences      → 默认路径是什么、是不是对的实例
```

`log/main` 尤其有用，`Permission denied` 这种关键信息只在这里出现：

```bash
./qb-mcp.sh api "log/main" --params '{"last_known_id":-1}'
```
